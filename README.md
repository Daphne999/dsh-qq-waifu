# dsh-qq-waifu

> 把 OPERIT 的 **Waifu 模式**搬到 QQ：一条回复切成几句，按打字速度逐条发出去。

## 它解决什么

AI 的回覆常常是一大段——结构清楚，但**不像人在聊天**。真人发消息是：

```
在的～
刚才在忙，没看到消息
怎么啦？
```

而不是一次甩过来三段话加一个小标题。

这个插件把"切碎 + 按节奏发"做成两个工具。

## 和 OPERIT 的对应关系

| OPERIT | 这里怎么实现 |
|---|---|
| 逐句发送（按标点切） | `waifu_say` 工具：切分 → 逐条发送 → 中间停顿 |
| 合并发送（连发多条合成一条） | 由 qqbot 的 debounce 补丁负责（入站侧） |
| 合并间隔 / 打字速度 | 配置项：`perCharMs` / `minDelayMs` / `maxDelayMs` |
| 绑定角色卡 | QQ 没有角色卡概念，用 preset / 人设代替 |

## 三个工具

| 工具 | 作用 |
|---|---|
| `waifu_split { text }` | 只预览会切成几条、每条之间停多久（不发送） |
| `waifu_say { text }` | 真正切分并逐条发送 |
| `waifu_status {}` | 看当前设置 |

## 配置

| 键 | 默认 | 说明 |
|---|---|---|
| `enabled` | `true` | 总开关；关掉后工具仍在但拒绝发送 |
| `maxChunks` | 5 | 最多切几条 |
| `minChunkChars` | 4 | 短于这个字数并进前一段（避免"嗯。""好。"刷屏） |
| `maxChunkChars` | 60 | 长于这个字数按逗号再切（避免一条顶屏幕） |
| `perCharMs` | 45 | 每个字折算多少毫秒"打字时间" |
| `minDelayMs` / `maxDelayMs` | 180 / 1800 | 单条停顿的上下限 |
| `notifyPath` / `notifyPort` | qq-notify 路由 / 自动探测 | 发送通道 |

## 安全设计

- **切分是纯函数**（`lib/splitter.mjs`），有单测覆盖短句合并、长句切逗号、上限截断
- **发送可中止**：外部要求停（比如用户又发了新消息）就不再往下发
- **失败即停**：某条发失败会返回"第几条失败"，不会把剩下的硬发出去
- **关掉开关就拒绝发送**，不会静默乱发

## 已知限制

- 依赖 qqbot 的 `qq-notify` HTTP 路由作为发送通道；如果那个入口没跑，`waifu_say` 会报错
- **不劫持** qqbot 的正常回复链路（那要改它的流式发送，风险高），所以"自动逐句"需要 agent 主动调用 `waifu_say`
- 入站合并要单独装 qqbot 的 debounce 补丁（`local/qq-debounce/`）
